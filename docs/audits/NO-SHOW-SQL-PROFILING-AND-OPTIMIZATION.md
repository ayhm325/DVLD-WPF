# No-Show SQL Profiling and Safe Optimization

**التاريخ:** 2026-11-09  
**النطاق:** فحص ساكن لمسار `NoShowProcessorService`، مخازن البيانات، وحدة العمل، وحدود عزل اختبارات SQL Server. هذه مراجعة وقياس مقترح فقط؛ لم تُعدّل الشيفرة أو الاختبارات أو قاعدة البيانات.

## 1. الخلاصة التنفيذية

يوجد في المسار الطبيعي لكل موعد مرشح عدة عمليات SQL منفصلة: أمر قفل التطبيق، قراءة الموعد مع `Test`، فحص وجود اختبار مرة أخرى، ثم تحديث الموعد. كما توجد قراءة لاختيار المرشحين مرة لكل دفعة. هذا يطابق سبب الاشتباه في N1-01، لكن لا توجد قياسات فعلية في هذه الجولة.

تعذر تنفيذ القياس بأمان لأن `DVLD_TEST_CONNECTION` غير مضبوط في البيئة الحالية؛ لا يمكن التحقق من وجهة خادم SQL. لذلك لم تُشغّل اختبارات أو تُفتح اتصالات قاعدة بيانات. الأرقام أدناه نموذج ساكن مستمد من تدفق التنفيذ، وليست نتائج تشغيل.

`GetForUpdateAsync` يحمّل بالفعل علاقة `Test` عبر `Include`. هذا يجعل استعلام `IsTestAlreadyTakenAsync` مرشحاً للحذف من ناحية عدد الاستعلامات، لكنه لم يُثبت بعد أن حذفه يحافظ على سلوك التنافس بين إنشاء الاختبار ومعالجة عدم الحضور. التوصية هي إبقاء الاستعلام إلى حين إضافة اختبار تكامل متزامن على SQL Server معزول يثبت سلامة جميع النتائج وحدود القفل.

## 3. التحقق من عزل الاختبارات

### ما يثبته الكود

- `SqlServerTestDatabase` يقرأ `DVLD_TEST_CONNECTION` فقط. إذا كان غائباً أو فارغاً، يرمي استثناء قبل فتح الاتصال.
- بعد تحليل الاتصال، يولّد اسم قاعدة جديداً بالشكل `DVLD_IntegrationTests_<GUID>` ويستخدمه كـ `InitialCatalog` في اتصال سياق الاختبارات.
- يستخدم `master` لاتصال إداري أثناء الحذف في teardown فقط، بينما قاعدة الاختبار نفسها تحمل الاسم العشوائي. وهذا يتفق مع السماح باتصال إداري إلى `master` وعدم استخدامه كقاعدة تنفيذ للاختبارات.
- اختبارات `AppointmentNoShowIntegrationTests` تستخدم fixture لإنشاء السياقات، وتتحقق من بادئة اسم القاعدة. لم يُعثر في مسار هذه الاختبارات على اتصال احتياطي مباشر إلى `DVLDf`.

### القيد الذي يمنع التشغيل

فُحص وجود `DVLD_TEST_CONNECTION` من دون عرض قيمة اتصال حساسة، وكانت النتيجة: **غير مضبوط**. لذلك لا يمكن التحقق من اسم الخادم أو المثيل الذي سيستقبل الاتصال، ولا يمكن إثبات وقت التشغيل أن الخادم المقصود هو خادم اختبار معزول. كما أن fixture يعيد تعيين `InitialCatalog` إلى اسم مولّد، لكن فحص الكود وحده لا يثبت هوية الخادم أو يستبعد خصائص اتصال غير متوقعة مثل إرفاق ملف قاعدة بيانات.

**القرار:** لم تُنفّذ اختبارات، أوامر SQL، أو أي اتصال بقاعدة بيانات. لم يحدث اتصال بـ `DVLDf` أو تعديل لها. يلزم توفير `DVLD_TEST_CONNECTION` يشير إلى خادم اختبار معتمد، ثم التحقق الآمن من المضيف/المثيل وخصائص الاتصال قبل التشغيل.

## 4. تصميم القياس المقترح

بعد تحقق العزل، يمكن إضافة أداة اختبارية مؤقتة أو اختبار قياس، بموافقة تنفيذ منفصلة، تتضمن:

1. `DbCommandInterceptor` مرتبطاً بسياق الاختبار يسجل لكل أمر EF: العدد، `CommandType`، فئة العملية (قراءة/إدراج/تحديث/إزالة/أخرى)، وقت التنفيذ، والنجاح أو الفشل/الإلغاء. يُجمع الزمن من callbacks المناسبة للأوامر المتزامنة وغير المتزامنة.
2. عدم تسجيل نص SQL الخام أو قيم المعاملات؛ تُخزن الفئة وبيانات الزمن فقط. إذا احتاج التصنيف بصمة للأمر، تُستخدم تسمية ثابتة لا تحتوي بيانات أو معاملات.
3. عدّ أمر `sp_getapplock` بشكل منفصل: `AcquireAppointmentLockAsync` ينشئ `DbCommand` مباشرة من `DbConnection` ويستدعي `ExecuteNonQueryAsync`، خارج مسار تنفيذ أوامر EF الذي يلتقطه `DbCommandInterceptor`. هذا استنتاج من مسار التنفيذ في الكود ومجال اعتراض أوامر EF؛ لذا لا يجوز اعتبار عدّ interceptor وحده إجمالي أوامر SQL. البديل الأكثر اكتمالاً هو SQL Server Extended Events على قاعدة الاختبار المعزولة، أو تغليف اختبارّي للاتصال/الأمر.
4. اختيار مصدر واحد باعتباره إجمالي SQL المرجعي لتجنب احتساب مزدوج عند الجمع بين interceptor وExtended Events. يمكن استخدام interceptor لتفصيل أوامر EF وExtended Events للتحقق من العدد الكلي وطلبات RPC.
5. فصل أحداث المعاملة (بدء/تثبيت/تراجع) عن عدّ أوامر SQL. لا تُحتسب أحداث المعاملة كأوامر إلا إذا رُصد أمر قاعدة بيانات فعلي صادر بشأنها.
6. تصفير القياس بعد إنشاء القاعدة والترحيلات وإضافة بيانات الاختبار، ثم تشغيل المعالج فقط. تسجيل حجم الدفعة، عدد المواعيد المختارة، والنتائج: `Processed` و`Ineligible` و`LockFailed` و`Failed`، مع إجمالي زمن التشغيل وتوزيع زمن الأوامر.
7. تكرار القياس مع 1 و10 و50 و100 موعد على الأقل عدة مرات، وتسجيل التشتت/الوسيط ومعلومات بيئة SQL Server. يجب أن تكون بيانات الاختبار مؤهلة فعلاً للمعالجة وألا تُحتسب أوامر التحضير ضمن النتيجة.

مرجع API: [Microsoft Learn — EF Core Interceptors](https://learn.microsoft.com/en-us/ef/core/logging-events-diagnostics/interceptors).

## 5. القياسات والفرق عن تقدير N1-01

**القياسات الفعلية: لم تُنفذ** بسبب غياب `DVLD_TEST_CONNECTION`. لا توجد أزمنة أو أعداد أو نتائج تشغيل فعلية في هذا التقرير.

النموذج الساكن لمسار النجاح المعتاد، وفق BatchSize=50:

| المواعيد الناجحة | استعلامات اختيار الدفعات المتوقعة ساكناً | عمليات لكل موعد وفق المسار | تقدير إجمالي ساكن | القياس الفعلي |
|---:|---:|---|---:|---|
| 1 | 1 | قفل تطبيق + قراءة موعد + فحص وجود Test + تحديث | 5 | لم يُنفذ |
| 10 | 1 | قفل تطبيق + قراءة موعد + فحص وجود Test + تحديث | 41 | لم يُنفذ |
| 50 | 2 (دفعة كاملة ثم استعلام فارغ للتوقف) | قفل تطبيق + قراءة موعد + فحص وجود Test + تحديث | 202 | لم يُنفذ |
| 100 | 3 (دفعتان كاملتان ثم استعلام فارغ) | قفل تطبيق + قراءة موعد + فحص وجود Test + تحديث | 403 | لم يُنفذ |

هذه الحسابات تتبع الصيغة `4N + S` حيث `S` عدد استعلامات انتقاء الدفعات. ويفترض كل موعد نجاحاً بلا إعادة محاولة أو فشل، وأن دفعة الحجم الكامل يعقبها استعلام فارغ لأن الحلقة تحتاج معرفة عدم وجود دفعة أخرى. قد يزيد العدد الفعلي بسبب إعادة المحاولة العابرة المفعلة عبر `EnableRetryOnFailure`، أو يختلف عند وجود مواعيد غير مؤهلة، تعارضات، إلغاء، أو فشل. لا ينبغي وصف هذه القيم بأنها نتائج SQL مقاسة.

لم تُقارن القياسات الفعلية بتقدير N1-01 لعدم توفرها. يمكن إجراء مقارنة صحيحة فقط بعد تشغيل التجربة المعزولة وتوثيق كيفية احتساب أمر القفل الخام وإعادة المحاولات.

## 6. حدود المعاملة والقفل والتنافس

- `ProcessSingleAppointmentAsync` يعالج المواعيد بالتتابع، ويفتح معاملة لكل موعد عبر `ExecuteInTransactionAsync` بمستوى `ReadCommitted`.
- أولاً ينفذ `sp_getapplock` بقفل حصري ومالك `Transaction` واسم مورد خاص بالموعد. هذا ينسق عمّال عدم الحضور الذين يستخدمون المورد نفسه؛ يحرر التثبيت أو التراجع القفل المرتبط بالمعاملة.
- ثم `GetForUpdateAsync` ينفذ `SELECT ... WITH (UPDLOCK, HOLDLOCK)` للموعد ويحمّل علاقة `Test`. بعد ذلك يعيد التحقق من الحالة والموعد والقفل، ثم يحفظ `NoShow` ويثبت المعاملة.
- `TestService` ينفذ إنشاء الاختبار في معاملة `Serializable` ويستخدم أيضاً تحميل الموعد المقفول ثم التحقق من وجود اختبار، قبل إضافة سجل الاختبار وتغيير حالة الموعد. قيد المفتاح الخارجي/العلاقة والفهرس على `TestAppointmentID` يضيفان حماية على مستوى قاعدة البيانات ضد سجل Test مكرر للموعد.
- استراتيجية EF لإعادة المحاولة قد تعيد تنفيذ وحدة العمل عند أخطاء عابرة؛ يجب أن يسجل القياس أوامر المحاولات الفعلية لا أن يفترض محاولة واحدة.
- توجد ملاحظة سلوكية تستحق اختباراً: بعض حدود الإلغاء تلتقط `Exception` وتحولها إلى نتيجة `Failed` بدلاً من تمرير `OperationCanceledException` إلى المستدعي. `ProcessBatchAsync` أيضاً يحول الاستثناء حول اختيار الدفعة إلى نتيجة خطأ. لا تغيّر ذلك ضمن تحسين عدّ الاستعلامات؛ أضف اختباراً يحدد السلوك المقصود.

## 7. تحليل استعلام وجود الاختبار المتكرر

`TestAppointmentRepository.GetForUpdateAsync` يحتوي `.Include(x => x.Test)`، لذا قراءة الموعد المقفول تجلب بيانات علاقة الاختبار. ومع ذلك، `NoShowProcessorService` يستدعي بعدها `TestRepository.IsTestAlreadyTakenAsync`، ما ينفذ استعلام `AnyAsync` مستقلاً.

قد يكون فحص `appointment.Test` بديلاً أقل كلفة عن الاستعلام المنفصل، لكن لا يمكن اعتبار الحذف آمناً اعتماداً على وجود Include فقط:

- استعلام انتقاء المرشحين نفسه يستبعد المواعيد التي لديها Test، لكنه لقطة سابقة لا تغني عن إعادة التحقق داخل المعاملة.
- قفل التطبيق مخصص لعمال NoShow، ولا يضمن وحده أن جميع مسارات إنشاء الاختبار تستخدم المورد نفسه.
- تحميل العلاقة مع `UPDLOCK, HOLDLOCK` على جدول الموعد لا يثبت بمفرده سلوك منع إدراج صف Test متزامن في كل سيناريوهات SQL Server والخطط والفهارس.
- مسار `TestService` يملك معاملة `Serializable` ويمسك صف الموعد عند القراءة؛ هذا دليل قوي على التنسيق داخل المسار الحالي، لكنه لم يُختبر مقابل NoShow في اختبار منافسة مخصص.
- فحص الحالة وإعادة التحقق، سلوك الإلغاء، إعادة المحاولة، ونتيجة كل موعد يجب أن تبقى مطابقة بعد أي تعديل.

**الاستنتاج:** الاستعلام الإضافي تكرار مرجح ومصدر واضح لعملية قراءة لكل موعد، لكنه **غير معتمد للحذف بعد**. أصغر تحسين محتمل هو استبدال استعلام `AnyAsync` بقرار مبني على علاقة `Test` المحملة، شريطة نجاح اختبار سباق SQL Server بين `TestService` وNoShow، واختبارات النتائج/التراجع/الإلغاء أدناه. إن لم يثبت الاختبار أن أحد المسارين ينتج نتيجة متسقة وحيدة بلا Test مفقود أو موعد NoShow مع اختبار، يُحتفظ بالاستعلام.

## 8. خطة اختبارات الانحدار المطلوبة

اختبارات التكامل الحالية تغطي نجاح التحويل إلى NoShow، حدود cutoff، حالات المواعيد، التكرار/Idempotency، عمال NoShow المتزامنين، غياب سجل الاختبار الوهمي، تحرير الموعد، الاستعادة عبر دفعات متعددة، وفشل القفل مع استمرار المعالجة. لكن لا يظهر اختبار صريح لعدّ SQL أو الإلغاء أو سباق `TestService` مقابل المعالج.

قبل اعتماد تحسين إزالة الاستعلام، أضف/أكمل على قاعدة SQL Server معزولة فقط:

| الحالة | التحقق المطلوب |
|---|---|
| معالجة ناجحة | يصبح الموعد NoShow مرة واحدة مع التاريخ الصحيح، وتكون النتيجة `Processed` |
| موعد عولج سابقاً | لا تتغير البيانات مجدداً؛ النتيجة غير مؤهلة/متخطاة وفق العقد الحالي |
| موعد له Test قائم | لا يتحول إلى NoShow، وتظل علاقة Test موجودة |
| عدة عمّال متزامنين | لا ينتج أكثر من انتقال ناجح أو بيانات متضاربة؛ توثيق LockFailed/Ineligible حسب الترتيب |
| TestService ينشئ اختباراً أثناء معالجة NoShow | نتيجة متسقة واحدة: إما اختبار وموعد مكتمل، أو NoShow بلا اختبار، وفق الترتيب الذي يحميه القفل؛ يمنع وجود سجلين/حالة متناقضة |
| تغير الحالة أثناء الانتظار | إعادة التحقق داخل المعاملة تمنع الكتابة فوق الحالة الأحدث |
| تراجع المعاملة | فشل/إلغاء بعد بدء التعديل لا يترك تحديثاً جزئياً أو قفلاً محجوزاً |
| الإلغاء | يثبت سلوك الإلغاء المتفق عليه، والتراجع وتحرير الأقفال وعدم تحويله بصمت إلى نجاح |
| عدد الأوامر | يثبت إجمالي الأوامر على أحجام 1/10/50/100، ويكشف الزيادة عن baseline؛ يميز أمر applock الخام عن أوامر EF وإعادات المحاولة |

اختبار عدد الأوامر ينبغي أن يكون متسامحاً مع اختلافات التنفيذ غير المؤثرة، لكن يثبت عدم عودة استعلام `AnyAsync` لكل موعد إذا اعتمد التحسين. لا تُضعف اختبارات التنافس الحالية، ولا تشغّل الاختبارات على `DVLDf` أو قاعدة يملكها المطور.

## 9. مقترح التحسين الأصغر

1. لا تغيّر الإنتاج الآن. اجعل القياس أول تغيير تنفيذي مستقل ومحصوراً ببنية الاختبارات، بعد إثبات إعداد اتصال SQL المعزول.
2. احصل على baseline فعلي للأحجام 1 و10 و50 و100، مع عدّ Extended Events أو آلية تلتقط `sp_getapplock` أيضاً.
3. أضف اختبار المنافسة بين `TestService` وNoShow واختبارات التراجع والإلغاء وتعداد الأوامر.
4. إذا أثبتت الاختبارات أن `Include(x => x.Test)` يوفر تحققاً حديثاً كافياً ضمن الأقفال والمعاملة الحالية، احذف فقط `IsTestAlreadyTakenAsync` من مسار NoShow، مع الإبقاء على استبعاد المرشحين، القفل، إعادة التحقق، المعاملة، وUnit of Work.
5. أعد القياسات نفسها وقارن الناجح والفاشل وإجمالي الزمن. إن لم تثبت السلامة أو لم يظهر فرق يستحق كلفة التغيير، أبقِ التنفيذ الحالي.

لا يوصى بتحديث جماعي، أو توازٍ بين المواعيد، أو حذف الأقفال، أو تجاوز Unit of Work، أو تغيير قاعدة البيانات/قواعد العمل.

## 10. المخاطر والقيود المتبقية

- لا يوجد اتصال SQL موثق أو إعداد `DVLD_TEST_CONNECTION` في البيئة الحالية، لذا تظل وجهة SQL الفعلية غير متحققة.
- لا توجد قياسات زمن أو أعداد فعلية ولا يمكن الجزم بأن أمر الوجود هو أكبر مساهم في الزمن.
- اعتراض EF وحده يفوّت أمر `sp_getapplock` المباشر؛ تصميم القياس يجب أن يعالج ذلك كي لا يقدم أرقاماً ناقصة.
- لم يُثبت اختبارياً التنافس بين إنشاء Test وNoShow، ولا سلوك الإلغاء في المسار الحالي.
- الحساب الساكن لا يشمل إعادة المحاولات العابرة أو أوامر التهيئة خارج نطاق القياس.
- لم تُشغّل اختبارات أو بناء. لم تُعدّل ملفات التطبيق أو الاختبارات أو الإعدادات أو قاعدة البيانات. أُنشئ هذا التقرير فقط، مع الحفاظ على ملف N1 غير المتتبع الذي كان موجوداً مسبقاً.

## 11. متابعة التنفيذ والتحقق (2026-11-09)

حاولت المتابعة تنفيذ المهمة بعد منح التفويض. لم يُعثر على `DVLD_TEST_CONNECTION` في بيئة العملية. أداة `SqlLocalDB.exe` موجودة، لكن `sqllocaldb info` أخفقت عند قراءة إعداد سجل LocalDB، لذلك لم تُعرف أسماء مثيلاته. كما تعذر تعداد خدمات Windows الخاصة بـ SQL Server لأن الوصول إلى Service Control Manager رُفض. وجود `sqlcmd` على الجهاز لا يثبت وجود خادم اختبار أو عزل قاعدة البيانات. لم تُعرض أي بيانات اعتماد، ولم يُجر اتصال.

ظهر أيضاً قيد في fixture الحالي يجب حسمه قبل استخدامه: `SqlServerTestDatabase.InitializeAsync` يبدل `InitialCatalog` إلى اسم عشوائي، لكنه لا يرفض أو يمسح `AttachDBFilename` من `SqlConnectionStringBuilder`؛ لذلك لا يضمن الكود وحده أن خيار إرفاق ملف لا يعيد توجيه الاتصال. كما لا يمكن التحقق من صلاحيات الحساب أو حصرها، بينما يقوم fixture بإنشاء/ترحيل قاعدة ثم يستخدم اتصال `master` الإداري لحذفها بصلاحيات واسعة. لم يُعدّل fixture لأن مصدر اتصال معتمد وخادم مستهدف لم يتوفرا للتحقق، وأي تغيير في بنية اتصال الاختبارات يحتاج اعتماداً خاصاً وفق حوكمة المستودع.

**حالة N1-01: PARTIALLY VERIFIED / BLOCKED، وليست CLOSED.** أُعيد التحقق ساكناً من مسار التنفيذ، وبقي فحص `IsTestAlreadyTakenAsync` دون تغيير لعدم وجود إثبات ديناميكي للتنافس. لم تُنفذ اختبارات تكامل أو وحدة أو بناء في هذه المحاولة؛ لم تُنشأ قاعدة أو يُنفذ SQL، ولم تُمس `DVLDf`.

**المتطلب الدقيق للاستئناف:** توفير `DVLD_TEST_CONNECTION` لخادم اختبار مخصص معتمد، وتأكيد هوية المضيف/المثيل وصلاحيات حساب الاختبار وحدود قاعدة البيانات. قبل تشغيل الاختبارات يجب معالجة/رفض خيارات الاتصال التي تسمح بالإرفاق أو إعادة التوجيه، وضمان أن الإنشاء والترحيل والتنظيف لا يستهدف إلا قواعد `DVLD_IntegrationTests_<GUID>` المملوكة للتشغيل الحالي. بعدها تُضاف اختبارات القياس والتنافس المطلوبة، ويُلتقط baseline فعلي قبل أي حذف للاستعلام.
